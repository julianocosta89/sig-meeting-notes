  - A big problem here is the combination of two issues: they want to check if the declared otel metrics have not changed, and also too that the prometheus translations of those names has not changed.  And the twist is, they want unchanging metric names even when they are declared incorrectly. For instance, an otel metric is declared with a unit in the name (counter to the spec), and then the translator correctly appends the unit, causing a doubling. We had to write a workaround to remove the extra suffix to fix their metric.  (And we can't fix the metric because that would break anyone using the native (incorrect) otel name)
  - The issue of otlptranslator behavior will be solved by unit tests.  The issue of otel name stability would have to be installed by some sort of test that can collect all metrics by all stable components.
  - So how do you know which components are stable?
  - Also, some components have dynamic labels.
  - We really really need translation strategy configuration in otel-go because that's going to  break things again
  - Require some additional data for components to specify what metrics need stability?
